agent-memory-sync

这套系统到底怎么运行

一句话：每个 agent 在会话开始时读同一份记忆，在会话中把值得记住的东西写回去； 服务器负责同步、存档和每天自动整理。下面按「谁在什么时候做什么」拆开讲。

2一天里的自动动作

按触发频率排。注意：dreaming 还没上 cron，目前只能手动跑。

每次会话
agent 先读 AGENT_PROTOCOL.md 和 MEMORY.md，知道你是谁、有什么偏好、 手上在做什么项目。会话中出现值得长期记住的事，由 agent 决定写进 log/（原始观察）或 projects/（项目上下文）。
每小时
本机 launchd 运行 archive-transcripts.sh，把各 agent 的转录同步到服务器， 只增不删。服务器 cron 运行 autocommit.sh， 把 vault 的改动提交成一条 auto: 时间戳 的 git commit。
每天（未上线）
dreaming 读取自上次运行以来的新转录和新 log，整理成记忆。 设计上是每天一次，但 roadmap 里明确要求「先手动运行几次，评估产出质量」—— 所以现在还是手动阶段。

3vault 里有什么，谁能写

同一个目录，不同层级的写入权限不同。这是整套系统的核心约束： 机器可以随手记项目上下文，但不能偷偷改你的画像和规则。

路径放什么谁能写
MEMORY.md 索引，一行一条，最多 200 行 用户确认后，agent 写
profile/ USER.md（身份、设备、常驻项目）、PREFERENCES.md（语言、沟通、UI、工具链） 用户确认后，agent 写
rules/ 被纠正过或被确认有效的工作规则，一条一个文件 用户确认后，agent 写
projects/ 跨设备、跨 agent 的项目背景：目标、约束、决定、进度 agent 可直接写
log/ 原始观察，按 YYYY-MM.<设备>.md 分文件，只追加 agent 随时写
proposals/ dreaming 想改 profile/rules 时生成的提案，等你确认 dreaming 新建，你处理
为什么这么分：projects/log 是可追溯的事实记录，写错了下一条能纠正； profile/rules 会影响所有 agent 的所有后续行为，写错一次就会被到处复制，所以必须人工过一道。

4dreaming 一次完整运行

这是最容易让人「没看懂」的部分。关键点是：headless agent 不能直接改你的 vault， 它只能改一份临时副本，最后由确定性的代码逐条比对、分类、写回。

  1. 收增量
    读取两类输入：vault 里自上次运行后新增的 log 段落；归档区里自上次文件偏移之后的新转录。 偏移记录在 .dream-state，所以同一批内容不会重复处理。
    为什么：每天看全量转录既慢又贵，偏移机制让每次只看新增部分。
  2. 解析与筛选
    按 agent 各自的转录格式解析，只保留用户亲手输入的消息和 agent 的回复； 工具调用、系统注入、子代理噪音被过滤。总输入受预算限制（默认 20 万字符），超了截断。
    为什么：转录 2.6G，其中绝大多数是工具输出，对提炼偏好没有价值。
  3. 在副本上整理
    把输入写成 input.md，连同 vault 的完整副本交给 headless agent （默认 claude -p，超时 1800 秒）。它按 vault/FORMAT.md 的格式要求， 只修改临时目录里的副本。
    为什么用副本：agent 可能出错、可能被转录里的内容带偏；副本保证原始 vault 不受影响。
  4. 按证据门槛取舍
    规则层要求同一要求出现两次以上，或用户明确说「以后都要……」「记住……」； 画像层只记用户明确陈述的事实，不做推断；已有且一致就跳过，补充就更新，推翻就标 superseded。
    为什么：一次性的说法不值得变成长期规则，宁缺毋滥。
  5. 闸门逐条分类
    确定性代码比对原件和副本，按路径把每个改动分成 A/B/C/拒绝四类（下一节）。 密钥扫描在这一步执行：gitleaks 缺失时直接 fail closed，拒绝写回。
    为什么不用 agent 自己判断：分类规则必须可验证、可复现，不能交给模型自由裁量。
  6. 写回与提交
    A 和 B 直接写回 vault 并提交；B 类改动单独成一个 commit，方便反悔时只 revert 那一块。 C 类不写回，生成 proposals/*.md 等你确认。删除、改已有 log、越权路径、疑似密钥一律拒绝。
    为什么：让「机器能自己做的事」和「必须人点头的事」在物理上分开。
  7. 出报告
    写到 ~/dream-reports/<时间>.md：新增、修改、标记过期各几条； 发现的可疑指令；转录里的敏感信息；拿不准而跳过的内容。
    为什么：无人值守任务必须留下可审计的痕迹，出了错能回看是哪一步判断错了。

失败语义

任何一步失败（agent 超时、闸门拒绝、密钥命中）都不推进 .dream-state， 下次重跑同一批增量。这保证不会因为一次失败就永久漏掉一段记忆。

5闸门：一个改动会走向哪里

只要你记住这张表，就理解了 dreaming 的全部安全边界。

级别改动结果
A MEMORY.md、log/ 末尾追加、新提案文件 直接提交
B projects/ 新增或修改；profile/rules 条目只标 superseded 直接提交，可单独 revert
C profile/rules 的其他新增或修改 转成提案，等你确认
拒绝 删除文件、改写已有 log、越权路径、符号链接、非 UTF-8、格式错误、疑似密钥 不写回

dry-run 是什么

加 --dry-run 会完整跑到闸门、生成报告，但不写回、不推进状态。 用来评估产出质量，比如 2026-11-17 那次：

A 1 条、B 2 条、C 2 条、过期 0 条；识别出转录里的注入指令没有执行； 识别出明文密码没有写入。

proposals 怎么处理

每次会话开始时，如果有未处理提案，agent 会用一句话提醒你，不展开。 你说「处理提案」后，逐条展示，按你的决定应用，并在提案文件里标注 accepted / rejected。

每个 agent 的全局指令文件里只写一句指示：先读协议，再读索引。 其余内容都从 vault 动态读取，所以改一次 vault，所有 agent 同时生效。
